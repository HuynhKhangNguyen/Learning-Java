All paths retain `/api/v1`. Adapter caller must first verify the public8080 HTTPS/mTLS edge identity. The verified edge must overwrite `X-Backend-Lab-Client-IP` with one resolved IP literal; missing/duplicate/hostname/list/ambiguous IPv4 forms are denied. Browser identity/forwarded headers are never authority. The private8443 listener rejects Origin/Cookie/client-IP headers; the transport profile stays foundation-only. This is not the actual production edge R31a or admission INT-01.

GET `/session` only reads bootstrap; it never creates/rotates a cookie or touches idle. Explicit credential bootstrap is **POST** `/session` with `X-Auth-Flow: credential`, exact configured HTTPS `Origin`, JSON body `{ "schemaVersion": 1 }` and the same content-type/body limits as commands (no query flag). Initial mint has no existing CSRF token; exact Origin/non-simple JSON/custom header protect this bootstrap, not any password mutation. GET with this flow header cannot mint. Valid existing preauth returns the same context/CSRF without Set-Cookie. Pending credential operation cannot reopen a flow.

This adds an explicit bootstrap method alongside API-I01's read-only GET; it is a technical adapter decision, not a new account/signup capability. [Fetch Origin algorithm](https://fetch.spec.whatwg.org/#append-a-request-origin-header) does not guarantee Origin on same-origin GET, so the browser must not attempt to set that forbidden header manually. The browser fixture verifies naturally emitted POST Origin; exact qualified runs are in evidence, not inferred from this specification.

Mutation headers: exact `Origin`, `Content-Type: application/json` optionally UTF-8 charset, `X-CSRF-TOKEN`; `Idempotency-Key` canonical lowercase UUID required for logout/reset/reauth/logout-all/password-change. Bodies are exact allowlists below, no unknown owner/role/passed/interactive fields. `schemaVersion` is integer1; `expectedContextId` canonical UUID string. JSON UTF-8/duplicate keys/surrogates/trailing documents use common strict codec; max4096 bytes, depth20. Password values are not trimmed/normalized; R03 policy/corpus/throttle still apply.

R04d opt-in source accepts proof only through its explicit sensitive authority after startup verification, not from a password-only branch. Capability flags describe the composition, not full leaf qualification. The response schema accepts boolean `identitySensitiveReauth`: false for standalone R04a and true only for that explicit canonical sensitive composition; it does not require true or grant a client permission.

R04d's **opt-in canonical composition** is owned-lab qualified as of13/10/2026; exact evidence/failures/limits remain in the task checkpoint, not in capability flags. POST `/auth/reauth` takes exact body `{schemaVersion:1, expectedContextId, password, purpose, intentHash}` plus canonical UUID `Idempotency-Key`, Origin/CSRF/cookie. Purposes are LEARNING_RESET, LOGOUT_ALL and PASSWORD_CHANGE; standalone/older constructors cannot enable the latter two. Password only reaches Identity's canonical reauth callback. Success returns ISSUED with opaque proof/grantRef/expiresAt/purpose/operationKey/intentHash, without Set-Cookie or learning reset commit. Canonical runtime shares verifier/corpus/stable configured key with the sensitive authority and verifies V7 before readiness. I04/I07 reuse the grant's exact key/context/purpose/payload. Exact consumed retries read the prior operation after TTL without fresh authorization, KDF, epoch/hash/idle renewal. ### Identity-sensitive intent v1 — opt-in source, qualification scoped by checkpoint

`IdentitySensitiveIntent` defines LOGOUT_ALL/PASSWORD_CHANGE command binding. Own `IdentitySensitiveAuthority` joins proof issuance/consume with account epoch/pending, old-session deny, token invalidation and two exact outboxes; forward V7's initially-deferred SQL guard rejects a consume without its local effects at commit. INT-06 remains Learning-only LEARNING_RESET and must never reserve an Identity-sensitive proof. Current source/verification and remaining acceptance are in the [R04d checkpoint](../../../docs/features/f10-identity-access/sessions/tasks/BL-R04d.md).

Client intent is lowercase SHA256 hex of UTF-8 bytes `identity-sensitive-intent-v1` followed by one zero byte, then four length-framed UTF-8 fields: action, canonical `expectedContextId`, canonical UUID `Idempotency-Key`, newPassword. Each field starts with its four-byte unsigned big-endian **byte** length. Logout-all has an empty final field and no password payload; password-change preserves password bytes without trimming or Unicode normalization and applies R03 code-point/Unicode policy. Length framing makes embedded newlines unambiguous. No owner/epoch claims from this hash grant permission: the authority must still compare canonical user/session/context/epoch/realm/purpose/key and deadlines under its locks.

Password-derived client hash must not be persisted or logged. `protectedDigest` derives a separate HMAC-SHA256 key using configured nonzero32-byte secret and label `identity-sensitive-storage-key-v1`, then HMACs the decoded32-byte intent hash. Own Identity stores only that keyed binding and recomputes it from the actual command. Secret stability across restart is required; raw proof/password/keys/hashes are not audit/error fields. No new configuration secret is introduced: the stable validated key is domain-separated from throttle use. Qualified V1–V7 migration files are not rewritten; later source changes require fresh affected qualification.

GET `/auth/operations/{operationId}` requires the initiating auth cookie and `X-Session-Context` UUID. It is status-only even after revoke/consumed preauth, no principal/CSRF/idle/cookie. Bootstrap under the initiating reset flow recovers a lost-response operationId; do not blindly repeat reset with a consumed flow (409), rotate its binding, or change its password again. Cookie/context mismatch is404 at authority. Logout retry uses exactly the original cookie/context/CSRF/key.

Auth cookie is `__Host-backend-lab-session`, 256-bit, Secure/HttpOnly/SameSite=Lax/Path=/ with no Domain. Only explicit preauth/login may emit it; Max-Age is bounded by the remaining DB-issued15m/12h deadline and Expires is that deadline. Expired issuance503 emits no deletion. Logout/status/activation/reset/bootstrap/background/late framework flush never Set-Cookie. Revoked cookie may remain in the browser without server authority.

Responses use schemaVersion1, known state, optional sessionContextId/csrfToken/userId/credentialEpoch (decimal string), operationId/statusPath as appropriate; unknown optional response fields are additive. REVOKING/EXPIRED must stay locked states, not be renamed PENDING_FENCES merely because they carry an operation. Errors carry code/traceId/messageKey, no input/password/token/cookie/SQL/stack echo. All responses no-store/nosniff; no wildcard credential CORS/preflight bypass.

Servlet adapter unit tests use authority doubles and prove parsing/header/dispatch/cookie/error decisions only. CMD04 Identity additionally requires `SessionRuntimeIT` and its actual browser report, beside transport regression. The browser fixture uses isolated installed Edge/Chromium, test-only TLS front relay and real Identity mTLS upstream; it is not production FE/cache/edge qualification. Body reads have a 3s connector budget; container failures use redacted JSON/no-store rather than HTML. Disconnects do not imply a completed mutation.

[Request schema](request.schema.json), [response schema](response.schema.json) and [non-secret examples](examples.json) are executable in the browser qualification fixture with the already locked dev validator.
